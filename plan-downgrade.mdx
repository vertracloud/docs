## How Downgrades Work

When you downgrade a Vertra Cloud plan, your **remaining days are converted** into equivalent days on the cheaper plan, in proportion to the price difference — no paid time is lost.

The unused value of the current plan is converted by the price ratio. Because the target plan costs less, you always end up with more days than you had.

<Info>
  Downgrades always move to the **immediately previous plan** in the hierarchy. You cannot skip plans.
</Info>

## Conversion Formula

Your remaining time is converted proportionally:

```
newDays = remainingDays × (currentPlanPrice / targetPlanPrice)
```

Since the target plan is cheaper, you always get **more days** than you had remaining.

### Example

<Card title="Pro 4 → Starter 2" icon="calculator">
  | | Value |
  |---|---|
  | **Current plan** | Pro 4 (R\$20.90/mo) |
  | **Target plan** | Starter 2 (R\$11.90/mo) |
  | **Days remaining** | 15 days |
  | **Converted days** | 15 × (20.90 ÷ 11.90) ≈ 26.34, rounded up to **27 days** on Starter 2 |
</Card>

## Plan Hierarchy

```
STARTER 1 → STARTER 2 → PRO 4 → PRO 6 → PRO 8 → BUSINESS 12 → BUSINESS 16 → BUSINESS 24 → ENTERPRISE 32 → ... → ENTERPRISE 512
```

<Warning>
  The **STARTER 1** plan cannot be downgraded further.
</Warning>

<Note>
  Downgrades only happen from **Account Settings**. The checkout never accepts a plan smaller
  than your current one — the plan picker hides them, and `POST /v1/orders` answers
  `400 NOT_AN_UPGRADE` for any order type that would shrink the plan.
</Note>

## Before You Downgrade

The system will check the following before processing:

<Steps>
  <Step title="Memory usage">
    Your total memory usage across all apps and databases must fit within the target plan's memory limit. If it exceeds, you'll need to reduce resource allocation first.
  </Step>
  <Step title="Docker images">
    The Docker images you have (your own and the ones image templates take, one per distinct image) must fit within the image slots of the target plan. If they exceed, delete images or image template apps first.
  </Step>
  <Step title="Rate limit">
    You can only downgrade once every **3 hours** to prevent abuse.
  </Step>
</Steps>

## What Changes on Downgrade

<AccordionGroup>
  <Accordion title="Resources & Limits">
    - Memory limit is reduced to the target plan's allocation
    - Apps and databases that exceed the new limit must be resized beforehand
    - CPU allocation is adjusted proportionally
  </Accordion>
  <Accordion title="Features">
    - Features exclusive to higher plans are immediately disabled
    - For example: custom domains, zero-downtime deploys, the database data manager, etc.
  </Accordion>
  <Accordion title="Workspaces">
    If downgrading from **Starter 2** to **Starter 1**, you will **lose the ability to create and manage workspaces**. Existing workspaces will be affected.
  </Accordion>
</AccordionGroup>

## Deploy History on Downgrade

When you downgrade, the earlier versions of your applications beyond the new plan's limit stop being available for rollback right away. Their code is deleted shortly after. Upgrading again does not bring back code that was already deleted. The version that is running is never affected.

See [Deploy history and rollback limits](/plans-and-limits#deploy-history-and-rollback-limits) for how many versions each plan keeps.

## Deploy Settings on Downgrade

Your application's automatic rollback and zero-downtime settings are not erased when you downgrade. The saved value stays on the application, but it only takes effect on a plan that includes the feature: automatic rollback from Pro, zero-downtime deploys from Starter 2. If you upgrade again, the saved values act again. While you are below the required plan, you can still turn either setting off, but not on.

## How to Downgrade

<Tabs>
  <Tab title="Via Dashboard">
    1. Go to **Dashboard → Settings → Account**
    2. Scroll to the **Downgrade Plan** section
    3. Review the target plan and confirm
  </Tab>
  <Tab title="Via API">
    ```bash
    curl -X POST \
      -H "Authorization: Bearer $VERTRA_API_KEY" \
      https://api.vertracloud.app/v1/users/me/downgrade
    ```

    **Possible responses:**
    - `200` — Downgrade successful
    - `400 DOWNGRADE_NOT_AVAILABLE` — Already on STARTER 1
    - `400 INSUFFICIENT_MEMORY_FOR_DOWNGRADE` — Reduce resource usage first
    - `400 INSUFFICIENT_IMAGE_SLOTS_FOR_DOWNGRADE` — The lower plan holds fewer Docker images than you use (image templates count): delete images or image template apps first
    - `429` — Rate limited (wait 3 hours)
  </Tab>
</Tabs>
