## What does an error look like?

Every error uses the same envelope, described in the [API introduction](/api-reference/introduction#what-does-a-response-look-like). The HTTP status tells you the category, `code` is a stable string safe to branch on, and `details` — when present — carries the numbers you need to act (a limit, a retry delay, the missing scope).

```json
{
  "code": "ERROR_CODE",
  "message": "Optional descriptive message",
  "details": { "retry_after": 30 }
}
```

Whenever `details.retry_after` is present, the answer also sends the `Retry-After` header with the same number of seconds.

`message` is for humans and can change; never branch your code on it. For deploy and runtime problems that don't come from the API itself (crash loops, missing dependencies, OOMKilled), see [Common Errors](/common-errors) — this page only covers the stable `code` values the API answers with.

<Note>
  `VALIDATION_ERROR` (`400`) covers request-shape problems across every route — a required field
  missing, the wrong type, an out-of-range value. `details.path` names the offending field, e.g.
  `"memory"` or `"user.name"`.
</Note>

## Auth & API keys

| Status | Code | Meaning & fix |
|---|---|---|
| 401 | `AUTH_TOKEN_MISSING` | No `Authorization` header was sent. Add `Authorization: Bearer <key>`. |
| 401 | `API_KEY_INVALID` | The key doesn't exist or its secret doesn't match. Check the key value, or create a new one in the dashboard. |
| 401 | `SESSION_REVOKED` | The dashboard session behind the token expired or was revoked (signed out, or ended from the sessions list). Sign in again. |
| 401 | `USER_NOT_FOUND` | The authenticated user no longer exists (rare — usually a deleted account). |
| 403 | `API_KEY_IP_DENIED` | The request's IP isn't in the key's `allowed_ips`. Add the caller's IP/CIDR to the key, or clear the list to allow any IP. |
| 403 | `API_KEY_MANAGED` | The key was created by the platform for a stack. It cannot be edited; it is revoked together with the stack. |
| 403 | `API_KEY_SCOPE_DENIED` | The key is missing the scope the route requires (`details.required`), or the route is dashboard-session only. See [Scopes](/api-reference/introduction#scopes). |
| 403 | `WEBSITE_ONLY` | The route only accepts a dashboard session. API keys normally get `API_KEY_SCOPE_DENIED` first on these routes; `WEBSITE_ONLY` is the second check behind it. No scope unlocks the action — use the dashboard. A certificate reset that would move an older database to the new address gets `WEBSITE_ONLY` straight away, even from an API key with the scope. |
| 403 | `ACCESS_DENIED` | You are a workspace member without the permission the action needs, or you did not send the `workspace_id`. A resource that was not found answers `404`, for example `APP_NOT_FOUND`. |
| 403 | `ACCOUNT_BANNED` | The account was banned. Contact support. |
| 403 | `APP_BANNED` | The application was banned. Contact support. |
| 403 | `DATABASE_BANNED` | The database was banned. Contact support. |
| 403 | `APP_SHIELD_COOLDOWN` | Vertra Shield paused the application after abusive traffic; `details` names the reason and cooldown end. Wait for the pause to end and fix the traffic source; start, restart, deploy, configuration and deletion stay blocked until then. See [Common Errors](/common-errors#platform-protections). |
| 404 | `USER_LIMITS_NOT_FOUND` | The account's plan limits couldn't be resolved. Contact support. |

### Build failure codes

When a build or install fails, `GET /v1/apps/{id}` returns the code in `last_build_error` (`null` after a successful build); the detail is in the application's logs.

| `last_build_error` | What to do |
|---|---|
| `INSTALL_OUT_OF_MEMORY` | Raise the application memory and try again. |
| `BUILD_FAILED` / `INSTALL_FAILED` | Read the logs and fix the project. |
| `BUILD_TIMEOUT` / `INSTALL_TIMEOUT` | Make the build or the installation shorter. |
| `BUILD_INTERRUPTED` | Try again. |
| `INSTALL_SHIELD_BLOCKED` | Network protection blocked traffic during the build; reduce the traffic the build generates. |
| `IMAGE_VOLUME_REFUSED` | The application's Docker image declares a path or permission the platform does not allow. Adjust the Dockerfile and publish a new version of the image. |
| `IMAGE_LABEL_REFUSED` | The application's Docker image uses a label reserved by the platform. Remove it from the Dockerfile and publish a new version of the image. |
| `IMAGE_PULL_FAILED` | The platform could not download the application's Docker image. Try again; if it keeps failing, publish a new version of the image. |

| 409 | `RESTORE_IN_PROGRESS` | A restore is running on the resource. Writes to it, including the database's Data tab, wait for it to finish; reading and deleting it are allowed. |
| 422 | `SNAPSHOT_CORRUPTED` | The snapshot does not match what was recorded when it was taken, so it cannot be restored. Nothing was changed; use another snapshot. |
| 500 | `SNAPSHOT_IMPORT_FAILED` | The restore failed while loading data into a database; it keeps the data it had before (a database just created from the snapshot stays empty), and the snapshot stays available to retry. |

| 429 | `SNAPSHOT_RATE_LIMITED` | Manual snapshot creation hit a limit: one snapshot per resource every 3 minutes, or the account's quota for any 24 hours (8 per GB of the plan's RAM, at least 2). `details.scope` is `resource` or `account`, with `retry_after`; `account` also has `resets_at`, the moment a slot frees up, in ISO 8601. |
| 429 | `RESTORE_COOLDOWN` | A restore or rollback was requested too soon after a previous one on the same resource (60 seconds for an application; for a database, 60 seconds for the user who asks and 120 seconds per database). It also applies when creating an application or a database from a snapshot. `details.retry_after` says how many seconds to wait. |

## General

| Status | Code | Meaning & fix |
|---|---|---|
| 400 | `VALIDATION_ERROR` | A parameter, query or body field failed validation; `details.path` names the field. |
| 400 | `INVALID_PARAMS` / `INVALID_PAYLOAD` / `INVALID_RANGE` | The request shape or a specific field is invalid for this route. |
| 403 | `FORBIDDEN` | The account isn't allowed to perform this action on this resource. |
| 400 | `MISSING_HEADERS` | A header the route requires wasn't sent. |
| 400 | `INVALID_JSON` | The body isn't valid JSON (a missing quote or comma, a trailing comma, single quotes). Validate the JSON and send it with `content-type: application/json`. |
| 400 | `EMPTY_BODY` | The request has `content-type: application/json` but no body. Send a JSON body (`{}` if the route has no required fields), or drop the `content-type` header on requests without a body. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | The `content-type` isn't one the route accepts. Send JSON with `content-type: application/json`; upload routes take `multipart/form-data`. |
| 400 | `BAD_REQUEST` | The request itself is malformed in a way no other code covers, for example a `Content-Length` that doesn't match the body. Fix the request and retry. |
| 408 | `REQUEST_TIMEOUT` | The request body didn't arrive in time. Retry, and check the connection if it keeps happening. |
| 500 | `INTERNAL_SERVER_ERROR` | Something failed on the platform side. Retry; if it persists, contact support with the request time. |

<Note>
  This catalog lists every code from the public API contract. A route can still answer other
  standard HTTP errors (like a generic `404` for an unknown path) that don't carry one of these
  `code` values.
</Note>
