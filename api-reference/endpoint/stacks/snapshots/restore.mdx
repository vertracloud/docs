Restores all the members together: databases first, then applications. The restore runs in the background and the request answers **`202`** as soon as it is accepted; nothing is restored yet. Needs the `stacks:write` scope when called with an API key.

<ParamField path="stack_id" type="string" required>
  The stack ID.
</ParamField>

<ParamField path="snapshot_id" type="string" required>
  The stack snapshot ID.
</ParamField>

<ParamField query="workspace_id" type="string">
  The workspace the stack belongs to, when you act on it as the workspace owner.
</ParamField>

<ParamField body="restore_image_version" type="boolean" default="false">
  Applications that run a custom image also go back to the image version of the snapshot, if it still exists.
</ParamField>

### Response

Unlike [Restore Application Snapshot](/api-reference/endpoint/apps/snapshots/restore), which restores one resource, this route starts one restore job per member that is still in the stack. Follow each `job_id` on [Get Snapshot Job](/api-reference/endpoint/apps/snapshots/jobs/get) (`GET /v1/users/{id}/snapshots/jobs/{job_id}`, where `{id}` is the job's `resource_id`) until its `status` is `ready` or `failed`. The stack is restored when all the jobs are `ready`.

The members are restored in order: databases first, and each application only after them. If a member fails, the members after it are **not** restored and their jobs fail with `STACK_RESTORE_MEMBER_FAILED`; the failed job has the real `reason`. The restore replaces the current data of each member for good: [create a snapshot of the stack](/api-reference/endpoint/stacks/snapshots/create) first if you may need it again.

Only that application's data is restored.

### Errors

If a member cannot be restored (for example it has a restore or a deploy in progress, or the snapshot does not fit), the request answers with that member's error and nothing is started. See [Restore Application Snapshot](/api-reference/endpoint/apps/snapshots/restore) for those codes.

| Status | Code | When |
|---|---|---|
| 403 | `WORKSPACE_OWNER_ONLY` | You are a workspace member, not the owner. |
| 404 | `STACK_NOT_FOUND` | The stack was not found. |
| 404 | `SNAPSHOT_NOT_FOUND` | The snapshot was not found or failed. |
| 409 | `OPERATION_IN_PROGRESS` | The stack snapshot is still `pending`: wait until it is `ready`. |
| 404 | `STACK_MEMBER_NOT_FOUND` | None of the snapshot's members is still in the stack. |

A job that ends `failed` after the `202` reports `STACK_RESTORE_MEMBER_FAILED` in its `reason` when a previous member failed, so this member was not restored.
