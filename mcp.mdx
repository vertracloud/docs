## What it is

Vertra Cloud's official MCP server (`@vertracloud/mcp`) gives your AI agent (Claude Code, Codex, Claude, Cursor,
VS Code, Gemini CLI and any other client that speaks the MCP protocol) the tools to deploy
applications, read logs, create databases and restore snapshots, always on your account and with
your API key. The agent acts within what the key allows; nothing beyond that.

Vertra doesn't host chat or an AI model: MCP is the official way for the agent **you** already use
to read context and operate the platform. To call the API directly from your own code, instead of
through an agent, use the [official SDKs](/sdks) (JavaScript, Python and Go).

## How do I connect my agent?

There are two ways, and you can use both:

| | Remote server | Local server |
|---|---|---|
| Address | `https://mcp.vertracloud.app/mcp` | `npx -y @vertracloud/mcp` on your computer |
| Sign-in | Your Vertra account in the browser (OAuth), or an API key in a header | An API key in `VERTRA_API_KEY` |
| Needs | Nothing installed | Node 18 or newer |
| Files on your computer | No: creating and deploying from a folder, downloads and uploads are left out | Yes, inside the project folder |
| Best for | Investigating, operating and configuring | Deploying the project you're working on |

Signing in through the browser creates an API key named after your agent with an `oauth:` prefix, visible and
revocable under **Settings → API keys** like any other key. An account has up to 10 keys.

To use an API key instead, go to **Settings → API keys** in the dashboard, create a key with the scopes the agent will
need (start with read scopes) and copy it: it's shown only once.

## Set up your client

Step-by-step guides with first prompts and troubleshooting: [Claude Code, Claude Desktop and claude.ai](/mcp/claude) and
[Codex](/mcp/codex). The summary for each client:

<Tabs>
  <Tab title="Claude Code">
    Remote, signing in through the browser:

    ```bash
    claude mcp add --transport http vertracloud https://mcp.vertracloud.app/mcp
    ```

    Then run `/mcp` inside Claude Code and choose **Authenticate**. To deploy from your folder, add the local server
    as well. See the [Claude guide](/mcp/claude).
  </Tab>
  <Tab title="Codex">
    Remote, in `~/.codex/config.toml`:

    ```toml
    [mcp_servers.vertracloud]
    url = "https://mcp.vertracloud.app/mcp"
    ```

    Then sign in with `codex mcp login vertracloud`. The Codex CLI, the IDE extension and the app read the same file.
    See the [Codex guide](/mcp/codex).
  </Tab>
  <Tab title="claude.ai and Claude Desktop">
    Open **Settings → Connectors → Add custom connector**, enter `https://mcp.vertracloud.app/mcp`, click
    **Connect** and sign in to your Vertra account. See the [Claude guide](/mcp/claude#claude-ai-and-claude-desktop).
  </Tab>
  <Tab title="Cursor">
    Local server, in `~/.cursor/mcp.json` (all projects) or `.cursor/mcp.json` (one project). Export
    `VERTRA_API_KEY` in your shell and open Cursor from the terminal (`cursor .`), so it reads the variable with `${env:...}`:

    ```json
    {
      "mcpServers": {
        "vertracloud": {
          "command": "npx",
          "args": ["-y", "@vertracloud/mcp"],
          "env": { "VERTRA_API_KEY": "${env:VERTRA_API_KEY}" }
        }
      }
    }
    ```

    Remote with an API key: `"vertracloud": { "url": "https://mcp.vertracloud.app/mcp", "headers": { "Authorization": "Bearer ${env:VERTRA_API_KEY}" } }`.
  </Tab>
  <Tab title="VS Code">
    In `.vscode/mcp.json`. VS Code asks for the key the first time and stores it securely:

    ```json
    {
      "inputs": [
        { "type": "promptString", "id": "vertra-key", "description": "Vertra Cloud API key", "password": true }
      ],
      "servers": {
        "vertracloud": {
          "type": "stdio",
          "command": "npx",
          "args": ["-y", "@vertracloud/mcp"],
          "env": { "VERTRA_API_KEY": "${input:vertra-key}" }
        }
      }
    }
    ```

    Check it with the **MCP: List Servers** command.
  </Tab>
  <Tab title="Gemini CLI">
    In `~/.gemini/settings.json` (all projects) or `.gemini/settings.json` (one project), with `VERTRA_API_KEY`
    exported in your shell:

    ```json
    {
      "mcpServers": {
        "vertracloud": {
          "command": "npx",
          "args": ["-y", "@vertracloud/mcp"],
          "env": { "VERTRA_API_KEY": "$VERTRA_API_KEY" }
        }
      }
    }
    ```

    Check it with `gemini mcp list`.
  </Tab>
  <Tab title="Other clients">
    Any MCP client works. For the local server, run `npx -y @vertracloud/mcp` with `VERTRA_API_KEY` in its
    environment. For the remote one, use the URL `https://mcp.vertracloud.app/mcp` (Streamable HTTP) with the header
    `Authorization: Bearer <your API key>`, or let the client sign in through OAuth if it supports dynamic client
    registration.
  </Tab>
</Tabs>

Then ask for something like "list my apps on Vertra". For prompts that work well, see

### Which consent screen is safe?

The consent screen always shows where access goes after you authorize: `claude.ai` and `chatgpt.com` marked as
verified, or **App on your computer** for agents that run locally (Claude Code, Codex). If it shows any other address
with an **Unverified app** warning, don't authorize unless you started that connection yourself. Scopes that reach
secrets, your content, billing or hard-to-undo actions are shown highlighted and **unchecked by default**: you have to
check them on purpose: `apps:envs`, `databases:credentials`, `apps:files`, `snapshots:read`, `blob:read`,
`apps:delete`, `databases:delete`, `images:delete`, `stacks:delete`, `billing:write`, `redeem:write`,
`workspaces:delete` and `workspaces:invites`.

<Note>
  The remote server leaves out the tools that read or write files on your computer: `create_app`, `deploy_app`,
  `download_app`, `upload_files`, `upload_blob`, `download_snapshot`, `create_image` and `rebuild_image`. Use the local
  server for them.
</Note>

### Local files stay in the project folder

Tools that read or write files on your computer only work **inside the folder the server was started in**. If your
client starts the server at the system root or your user folder, set `VERTRA_MCP_ROOT` to the project folder, next to
`VERTRA_API_KEY`. Files outside it, and credential folders such as `.ssh` and `.aws`, are refused even if the agent asks
for them. Nothing is overwritten.

## What the key and scope control

Every tool requires a specific key scope (see [Scopes](/api-reference/introduction#scopes) for
the full list). Without the scope, the call fails with `API_KEY_SCOPE_DENIED` instead of acting on
the resource. This applies equally to a key pasted in manually and to a key created through
claude.ai's OAuth flow.

- **`list_envs` never returns the value of an environment variable** — only the names. There's no
  tool that reads a variable's value or a database's connection string without the
  `databases:credentials` scope explicitly checked.
- **Orders and code redemption** use the billing scopes: `billing:read` lists orders, checks
  status and reads your billing details, `billing:write` creates a plan order, generates the PIX code
  and saves your billing details (name, address and CPF/CNPJ — only when you provide them), `redeem:write` redeems
  a promo code. You're the one who pays the PIX, in your bank's app — the assistant never pays
  anything. Orders are for 1, 3, 6 or 12 months. `list_plans` reads the plans on sale straight from the API, without
  a scope, and `quote_order` (`billing:read`) prices a plan and period, with an optional coupon, without creating an
  order. Card payments and saved cards are only available in the dashboard.
- **Workspaces**: `delete_workspace` requires `workspaces:delete`; listing/revoking, viewing,
  accepting, and declining an invite require `workspaces:invites`. Both scopes only enter through
  the `full` preset (or a custom selection) and appear unchecked on claude.ai's authorization
  screen.
- **Switching to a lower plan (downgrade) isn't a tool.** It remains a dashboard-only action, with
  or without an API key.
- **Tools that delete, overwrite, stop, restart or change access are marked destructive** for the client,
  so most clients ask you to confirm before running them. Examples: `delete_app`,
  `stop_app`, `restart_app`, `unpublish_app`, `remove_domain`, `set_env`, `write_file`, `upload_blob`
  and `set_blob_visibility`.
- **Content that comes from your applications is marked as untrusted.** Logs, file contents, release
  logs, deploy messages and blob paths reach the assistant inside an `untrusted_content` block, so a
  line written by your app is read as data, not as an instruction.
- **The server never follows redirects**, so your API key is only ever sent to the Vertra Cloud API.

## Organize folders and favorites

MCP can also organize applications and databases with folders and favorites persisted on the
account. Personal organization uses `account:read`/`account:write`; organization within a
workspace uses `workspaces:read`/`workspaces:write`.

This organization is individual. An action done through MCP only changes the authenticated user's
view within the chosen scope. MCP doesn't mix folders with Flow groups: groups remain elements of
the local canvas and aren't synced or migrated.

Creating, renaming, recoloring, or deleting a folder, moving an application or database, and
favoriting or unfavoriting generates an activity. The tool doesn't receive or make up `origin` or
`author_id`; the API logs the call by API key automatically.

## Creating applications

Creating an application is asynchronous: `create_app` returns right away with the application in
`building`, and install and build continue in the background.

| Tool | What it does | Scope |
|---|---|---|
| `wait_for_app` | Waits up to `timeout_seconds` (1–25) for an application to leave `building`. Returns the application: `up` (ready), `down` (build failed; `last_build_error` says why, and `get_logs` has the detail) or still `building` (call again). Accepts `workspace_id` | `apps:read` |

While an application is building, start, stop, restart, deploy, rollback and similar actions return
`409 APP_BUILDING`. Call `wait_for_app` first.

## Releases, rollback and deploy settings

The assistant can read an application's deploy history and go back to an earlier version. See the
[rollback and zero-downtime guide](/guides/rollback-and-zero-downtime-deploys) for how releases work.

| Tool | What it does | Scope |
|---|---|---|
| `list_releases` | Versions of an application, newest first, with status, message, author and whether each can be restored | `apps:read` |
| `get_release_log` | Log recorded for a version that failed | `apps:read` |
| `preview_rollback` | Shows which environment variables a rollback would add, change or remove. Names only, never values | `apps:envs` |
| `rollback_app` | Returns the code to an earlier version and restarts. Data the app wrote while running stays | `apps:write` (plus `apps:envs` with `restore_environment`) |

`rollback_app` is destructive, so the client asks you to confirm before running it. Rollback is available on every plan. Environment variables are kept as
they are unless `restore_environment` is true, so run `preview_rollback` first in that case.

Two existing tools grew: `update_app_config` accepts `zero_downtime`, `auto_rollback` and `health_check_path`
(plan limits apply), and `deploy_app` accepts a `message` that appears in the deploy history.

## Web Analytics

The assistant can read the Web Analytics of an application's site. See [Web Analytics](/web-analytics/overview) for what each view means.

| Tool | What it does | Scope |
|---|---|---|
| `get_app_analytics` | Traffic: requests, visits, bytes, error rates, a time series and the top entries per dimension. Accepts the period, filters, `compare`, `compare_start` and `breakdowns` | `apps:read` |
| `get_app_analytics_errors` | Errors: totals, error rate, a time series, the paths with the most errors and the spread by status. `include_4xx` adds 4xx | `apps:read` |
| `get_app_analytics_performance` | Latency at the edge and in the container, slowest paths and problems by path. Needs a plan with the Performance view | `apps:read` |
| `list_app_analytics_requests` | One page of the request log; `cursor` returns the next page. Needs a plan with the Requests view | `apps:read` |

Paths, referers and network names come from your visitors, so they reach the assistant inside an `untrusted_content` block.
If the plan does not include a view, the call fails with `PLAN_DOES_NOT_SUPPORT_WEB_ANALYTICS_PERFORMANCE` or
`PLAN_DOES_NOT_SUPPORT_WEB_ANALYTICS_REQUESTS`; a period before the plan's history fails with `ANALYTICS_RANGE_EXCEEDS_PLAN`;
and `ANALYTICS_BUSY` means to try again after `details.retry_after` seconds.

## Blob Storage

The assistant can work with your [Blob Storage](/blob/overview) files.

| Tool | What it does | Scope |
|---|---|---|
| `list_blob_objects` | Lists files, optionally inside a folder (`prefix`) | `blob:read` |
| `get_blob_object` | Path, size, type, visibility and public URL of one file | `blob:read` |
| `blob_download_url` | Temporary download link, for private files too. It expires and can't be revoked | `blob:read` |
| `blob_stats` | Used and total space, and the limits of the plan | `blob:read` |
| `upload_blob` | Uploads a file from your computer, up to 100 MB, private by default. `rename_on_conflict` saves a taken name as `name-1.ext` | `blob:write` |
| `set_blob_visibility` | Switches a file between public and private | `blob:write` |
| `delete_blob_object` | Deletes one file; its public URL stops working | `blob:write` |

`upload_blob` is local-only, like the other upload tools, and refuses secret and credential files such as `.env`,
keys and `.git`.

## What's left out

The server only talks to Vertra Cloud's public API and has no permissions of its own — the key is
the boundary of everything the assistant can do. These are always left out of every tool:

- **Container terminal** and running commands inside the application.
- **The database Data tab** (SQL console, collections, keys) — dashboard only.
- **Creating a workspace invite, transferring ownership, and approving/rejecting action
  requests** — dashboard only. The assistant can list and revoke invites, accept or decline an
  invite, delete a workspace, and *request* an action, but a person always decides the request.
- **GitHub linking** (authorizing, deauthorizing, choosing the auto-deploy repository).

## Common issues

| What shows up | What it is | What to do |
|---|---|---|
| `NOT_AUTHENTICATED` | No key was sent | Check `VERTRA_API_KEY` in the client's configuration, or sign in again on the remote server |
| `API_KEY_INVALID` | The key is wrong or was revoked | Locally, check `VERTRA_API_KEY`; on the remote server, sign in again to create a new key |
| `API_KEY_SCOPE_DENIED` | The key doesn't have that tool's scope | Create a new key, or sign in again, checking the needed scope |
| `RATE_LIMIT_EXCEEDED` / `DAILY_QUOTA_EXCEEDED` | The plan's per-minute or per-day request limit | Wait for `retry_after` seconds and try again |
| `PATH_OUTSIDE_ROOT` or `ROOT_TOO_BROAD` | The file is outside the allowed folder | Set `VERTRA_MCP_ROOT` to the project folder |
| `DEST_EXISTS` | A file already exists at that path | Choose another name; nothing is overwritten |
| `create_app` or `deploy_app` doesn't show up | You're on the remote server | Add the local server too |
| The local server doesn't start, or times out on the first run | Node below 18, or `npx` still downloading the package | Update Node; on Codex, raise `startup_timeout_sec` |
| The key limit was reached | An account has up to 10 API keys, and each OAuth sign-in creates one | Revoke unused keys under **Settings → API keys** |
