### Roll back an application to an earlier version

The **Deploys** tab now lets you go back to an earlier version of an application's code. Pick a version and confirm: the application returns to the code it had in that version and restarts.

- **What comes back:** all the code of that version. Code files the version did not have are removed.
- **What stays:** data the application created while running, such as a database file or uploads. To bring data back, use a snapshot.
- **Environment variables (optional):** check the option to restore the variables saved with that version. The confirmation lists only the names of the variables that will be added, changed or removed. Values are never shown.
- **Undo:** a rollback is a new version in the history, so you can roll back to the version you came from. Two rollbacks of the same application need 30 seconds between them.
- **Limits by plan:** rollback starts on Pro. Pro keeps the 3 previous versions for 7 days, Scale 5 for 14 days, Intermediary 10 for 30 days, and Enterprise 15 to 30 by tier for 30 days. A version's time starts when it stops running; the running version never expires. Economy and Free show the history without the rollback option.

The API has a [preview](/api-reference/endpoint/apps/releases/rollback-preview) of the variable changes and a [rollback](/api-reference/endpoint/apps/releases/rollback) endpoint. Rolling back needs the `apps:write` scope, plus `apps:envs` when restoring variables.

### Deploy history and commit messages for every application

Each application now has a **Deploys** tab in the dashboard. It lists every version of the application's code, whatever its source: a push to GitHub, the CLI, an upload from the dashboard or the API, or an edit in the file manager. Each entry shows its status, message, author, date and build time. The tab is available on every plan.

The history starts with the first code submission after this update. Applications created from a snapshot do not get an initial entry. Edits made in the file manager are grouped into the history at the next restart or code submission.

You can write a message for each version:

- **Dashboard:** an optional message field in the upload dialog.
- **API:** a `message` field on the file upload endpoint.
- **CLI:** `vertra app commit -m "..."`. Without `-m`, inside a git repository, the CLI uses the subject of the latest commit.

The API exposes the same history to your tools. [List releases](/api-reference/endpoint/apps/releases/list) returns the versions of an application, and [release log](/api-reference/endpoint/apps/releases/log) returns the log of one of them. Both require the `apps:read` scope. The Go SDK adds `Apps.Releases()` and a `Message` field on uploads.

### Auto-deploy from GitHub builds the commit you pushed

Auto-deploy from GitHub now builds exactly the commit that was pushed. Before, the build took whatever was at the tip of the branch when the download started, so two pushes close together could show one commit in the deploy history while a newer one was running. Each deploy now matches the commit it lists.

A push that deletes the `main` or `master` branch no longer starts a deploy.
