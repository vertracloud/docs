### The new version in the console during a zero-downtime deploy

During a zero-downtime deploy, the console shows the lines of the new version (installation, build and start) together with the lines of the version that is serving, in the order they happen, with the new version's lines marked **[New version]**. When the new version takes over, it becomes the console's version right away, without waiting for the previous one to finish leaving. The metrics strip shows the new version next to the current one, as an inner ring and a value marked "new", until it takes over or is discarded. If you reload the page during the deploy, the lines of both versions stay in order.

### Zero-downtime deploy needs free memory in the plan

The new version of a zero-downtime deploy runs next to the current one, so it now only happens when the plan has free memory at least equal to the application's memory. Free memory is the plan's total minus the memory of all your applications and databases, including those in workspaces. Nothing is reserved: it is checked on every restart and deploy. Without enough free memory, the application restarts the regular way (stop, then start) and the console says why. In **Settings → Deploy**, the zero-downtime setting shows how much free memory it needs and how much the plan has.

### Rebuild an image answers right away

**Rebuild** on a custom Docker image now responds immediately and shows "Downloading the repository code" until the build enters the queue. If the repository or the stored context cannot be used (for example, the linked branch no longer exists), the build ends as failed and the image shows the reason, instead of the request failing.

### Metrics strip

The numbers in the metrics strip stay aligned when you select a value.

### Saved logs

In the **Logs** tab, the log saved when a zero-downtime deploy switches versions now shows both versions the way you saw them in the console: the lines of the version that was serving and the lines of the new version, in the order they happened, with the new version's lines marked **[New version]**. The log of a new version that was discarded marks its lines the same way. In the file itself, in the file manager or downloaded, those lines start with `[new version]`.

### API: `next_metrics` and the `preparing` phase

- `GET /v1/apps/{id}/realtime` sends `next_metrics` events, with `metrics=true`: the same live reading as `metrics`, for the new version during a zero-downtime deploy, until it takes over or is discarded. `metrics` keeps describing the version that is serving.
- Images have a new build phase, `build_phase: "preparing"`, before `queued`: the platform is getting the code of the build. `POST /v1/images/{image_id}/rebuild` responds `202` right away with the image in `building`/`preparing`, and a problem with the source no longer fails the call: the build ends as `failed` and the image returns the code in `error_code` (`FETCH_ZIP_ERROR`, `INSTALLATION_NOT_FOUND`, `IMAGE_CONTEXT_TOO_LARGE` or `DOCKERFILE_REFUSED`) and the findings in `error`. `IMAGE_NOT_READY` is still returned right away when the image never stored its code.
