### La creación de aplicaciones responde al instante y el build continúa en segundo plano

Crear una aplicación ya no mantiene la petición abierta hasta que terminan la instalación y el build. `POST /v1/apps` responde ahora de inmediato con `202 Accepted` y la aplicación en el nuevo estado `building`; el build continúa en segundo plano con logs en vivo. Cuando termina, la aplicación pasa a `up`, o a `down` si la instalación o el build fallaron, con la salida en sus logs.

- **Seguir el build:** consulta `GET /v1/apps/{id}` o abre los [logs en tiempo real](/es-es/api-reference/endpoint/apps/realtime).
- **Durante el build:** iniciar, detener, reiniciar, los despliegues de archivos, el rollback, los snapshots, las restauraciones y los cambios de configuración responden `409 APP_BUILDING`. Eliminar la aplicación sí está permitido.
- **Builds interrumpidos:** la aplicación permanece en `down` y aparece `BUILD_INTERRUPTED` en sus logs. Si la plataforma cancela la creación, la aplicación deja de existir.
- **Motivo del fallo:** cuando un build o una instalación fallan, `GET /v1/apps/{id}` devuelve el código en el nuevo campo `last_build_error` (`null` tras un build correcto). Los helpers de espera de los SDK, el servidor MCP, la CLI, la extensión de VS Code y el panel lo usan para indicar qué hacer. Consulta [Errores](/es-es/api-reference/errors#códigos-de-fallo-del-build).
- **Cambios en la respuesta:** la respuesta de creación ya no incluye `removed_directories`, y `GET /v1/apps/{id}` devuelve `missing_dependencies` después del build.
- **SDK, MCP y CLI:** `apps.waitUntilReady` (JavaScript), `apps.wait_until_ready` (Python) y `Apps.WaitUntilReady` (Go) esperan a que termine el build. El servidor MCP tiene una nueva herramienta `wait_for_app`, y la CLI acepta `--no-wait`. Consulta la [guía de SDK](/es-es/sdks) y [MCP](/es-es/mcp).

Consulta [Crear aplicación](/es-es/api-reference/endpoint/apps/create) y [Errores](/es-es/api-reference/errors).

### Los builds instalan devDependencies cuando hay un comando de build

Cuando una aplicación tiene un comando de build, la instalación de dependencias incluye `devDependencies`, de modo que herramientas como Tailwind, TypeScript o PostCSS funcionan sin tener que pasarlas a `dependencies`. Sin comando de build, solo se instalan `dependencies`, como antes.

### Builds más rápidos

La instalación de dependencias y los builds son ahora más rápidos, sobre todo en proyectos grandes.

### Puppeteer usa el Chromium preinstalado

Puppeteer usa ahora el Chromium que ya viene incluido en la imagen del runtime, así que la instalación ya no descarga ningún navegador.

### Correcciones de runtime para Ruby, Java, PHP y Rust

- **Ruby:** las gemas instaladas desde el Gemfile se cargan ahora automáticamente al iniciar, así que ya no necesitas `require "bundler/setup"`. Las aplicaciones también se ejecutan con `RACK_ENV` y `RAILS_ENV` definidos como `production`, de modo que las apps de Sinatra ya no responden `403 Host not permitted`; ambas variables están ahora reservadas, igual que `NODE_ENV`.
- **Java:** los proyectos Maven y Gradle se compilan en la plataforma, ya que el runtime incluye ahora un JDK.
- **PHP:** añadir un paquete a `composer.json` sin actualizar `composer.lock` ya no hace fallar la instalación; el archivo de bloqueo se actualiza.
- **Rust:** el runtime se actualiza a 1.98 (recomendada) y 1.99 (la más reciente); 1.97 sigue disponible.
