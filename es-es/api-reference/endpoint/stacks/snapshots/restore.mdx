Restaura todos los miembros juntos: primero las bases de datos, después las aplicaciones. La restauración corre en segundo plano y la petición responde **`202`** en cuanto se acepta; todavía no se ha restaurado nada. Necesita el scope `stacks:write` cuando se llama con una clave de API.

<ParamField path="stack_id" type="string" required>
  El ID del stack.
</ParamField>

<ParamField path="snapshot_id" type="string" required>
  El ID del snapshot del stack.
</ParamField>

<ParamField query="workspace_id" type="string">
  El workspace al que pertenece el stack, cuando actúas sobre él como propietario del workspace.
</ParamField>

<ParamField body="restore_image_version" type="boolean" default="false">
  Las aplicaciones que ejecutan una imagen personalizada también vuelven a la versión de la imagen del snapshot, si todavía existe.
</ParamField>

### Respuesta

A diferencia de [Restaurar snapshot de la aplicación](/es-es/api-reference/endpoint/apps/snapshots/restore), que restaura un recurso, esta ruta inicia un job de restauración por cada miembro que sigue en el stack. Sigue cada `job_id` en [Obtener job de snapshot](/es-es/api-reference/endpoint/apps/snapshots/jobs/get) (`GET /v1/users/{id}/snapshots/jobs/{job_id}`, donde `{id}` es el `resource_id` del job) hasta que su `status` sea `ready` o `failed`. El stack queda restaurado cuando todos los jobs están `ready`.

Los miembros se restauran en orden: primero las bases de datos, y cada aplicación solo después de ellas. Si un miembro falla, los miembros siguientes **no** se restauran y sus jobs fallan con `STACK_RESTORE_MEMBER_FAILED`; el job que falló trae el `reason` real. La restauración sustituye para siempre los datos actuales de cada miembro: [crea un snapshot del stack](/es-es/api-reference/endpoint/stacks/snapshots/create) antes si puedes necesitarlos de nuevo.

Solo se restauran los datos de esa aplicación.

### Errores

Si un miembro no se puede restaurar (por ejemplo, tiene una restauración o un despliegue en curso, o el snapshot no cabe), la petición responde con el error de ese miembro y no se inicia nada. Mira [Restaurar snapshot de la aplicación](/es-es/api-reference/endpoint/apps/snapshots/restore) para esos códigos.

| Estado | Código | Cuándo |
|---|---|---|
| 403 | `WORKSPACE_OWNER_ONLY` | Eres miembro del workspace, no el propietario. |
| 404 | `STACK_NOT_FOUND` | El stack no se encontró. |
| 404 | `SNAPSHOT_NOT_FOUND` | No se encontró el snapshot o falló. |
| 409 | `OPERATION_IN_PROGRESS` | La snapshot del stack sigue `pending`: espera a que esté `ready`. |
| 404 | `STACK_MEMBER_NOT_FOUND` | Ninguno de los miembros del snapshot sigue en el stack. |

Un job que termina `failed` después del `202` informa `STACK_RESTORE_MEMBER_FAILED` en su `reason` cuando un miembro anterior falló, así que este miembro no se restauró.
