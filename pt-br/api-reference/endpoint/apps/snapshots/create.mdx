---
title: Criar snapshot da aplicação
sidebarTitle: Criar snapshot
api: POST https://api.vertracloud.app/v1/users/{id}/snapshots
authMethod: bearer
description: Faz um snapshot de uma aplicação ou banco de dados agora. Responde 201 com o snapshot, ou 202 com um job para acompanhar quando demora mais de 90 segundos.
---

{/* @see success/error — @vertracloud/api-types */}
<ParamField path="id" type="string" required>
  O ID da aplicação ou do banco de dados a ser salvo em snapshot.
</ParamField>

<ParamField query="scope" type="string" required>
  O tipo do recurso. Valores possíveis: `applications`, `databases`.
</ParamField>

<Note>
  **Três limites se aplicam aos snapshots manuais.** Cada usuário pode pedir um a cada **5 segundos**; o mesmo recurso pode
  receber um snapshot a cada **3 minutos**; e a conta tem uma cota em qualquer janela de **24 horas**, contada a partir de cada snapshot
  (a vaga volta 24 horas depois de usada, não à meia-noite): **8 por GB de RAM do plano, no mínimo 2**, somando todos os
  seus recursos (8 no Starter 1, 16 no Starter 2, 32 a 64 no Pro, 96 a 192 no Business). Não há limite diário por recurso. Pedir de novo
  em menos de 5 segundos responde o `429 RATE_LIMIT_EXCEEDED` genérico, com `retry_after`. Ao ultrapassar o limite do recurso ou da conta,
  a API responde `429 SNAPSHOT_RATE_LIMITED` com `details.scope` (`resource` ou `account`) e
  `details.retry_after` em segundos; com `account`, `details` traz também `resets_at`, o momento em que uma vaga volta, em ISO 8601.
  O backup diário do seu plano não usa a cota. Veja [Limite de requisições](/pt-br/api-reference/introduction#como-a-api-tem-limite-de-taxa).
</Note>

Enquanto uma aplicação recebe um snapshot, deploys, rollbacks, reinícios, inícios, paradas, mudanças de variáveis de ambiente, restaurações e as escritas do gerenciador de
arquivos respondem `409 OPERATION_IN_PROGRESS`; tente de novo em instantes.

### Resposta

O snapshot fica pronto em até 90 segundos na maioria dos casos: a resposta é **`201`** com o snapshot. Quando demora mais, a
resposta é **`202`** com um `job_id`: não é um erro e o snapshot continua sendo feito. Acompanhe
`response.job_id` em [Obter job de snapshot](/pt-br/api-reference/endpoint/apps/snapshots/jobs/get); o snapshot aparece na
[lista](/pt-br/api-reference/endpoint/apps/snapshots/getall) quando fica pronto. Os clientes devem tratar as duas respostas.

  </ResponseField>

  <ResponseField name="size" type="number">

  </ResponseField>

  <ResponseField name="resource_name" type="string | null">
    O nome que o recurso tinha no momento em que o snapshot foi feito.
  </ResponseField>

  <ResponseField name="created_at" type="string">
    Quando o snapshot foi feito.
  </ResponseField>

  <ResponseField name="expires_at" type="string">
    Quando o snapshot será excluído automaticamente.
  </ResponseField>

  <ResponseField name="origin" type="string">
    O que fez o snapshot: `manual` (você) ou `automatic` (o backup diário do plano, ou o snapshot que a plataforma tira antes de remover um recurso, por exemplo quando o plano vence). Ausente em snapshots antigos.
  </ResponseField>

</ResponseField>

### Respostas de erro

<ResponseField name="code" type="string">
  O código de erro que indica o motivo da falha. Valores possíveis:
  - `AUTH_TOKEN_MISSING`, `API_KEY_INVALID`, `SESSION_REVOKED`: o header `Authorization` está ausente, a chave de API é inválida ou a sessão do painel foi revogada (`401`).
  - `API_KEY_IP_DENIED`, `API_KEY_SCOPE_DENIED`: a chave de API é usada a partir de um IP fora da sua allowlist, ou não tem o escopo que a rota exige (`403`).
  - `USER_NOT_FOUND`: o usuário autenticado não foi encontrado.
  - `APP_NOT_FOUND`: a aplicação informada não foi encontrada.
  - `DATABASE_NOT_FOUND`: o banco de dados informado não foi encontrado.
  - `ACCESS_DENIED`: você é membro de um workspace sem a permissão para esta ação, ou não enviou o `workspace_id` (`403`).
  - `PLAN_NOT_ALLOWED`: o plano da conta não inclui snapshots manuais (`403`).
  - `DATABASE_NOT_RUNNING`: o banco de dados precisa estar em execução para gerar um snapshot (`409`). O Redis não tem essa exigência.
  - `DATABASE_NOT_READY`: o banco de dados ainda não está pronto (`503`). Tente de novo em instantes; a vaga da cota é devolvida.
  - `APP_BUILDING`: a aplicação está em build ou deploy (`409`). Tente de novo quando terminar.
  - `RESTORE_IN_PROGRESS`: há uma restauração em andamento neste recurso (`409`).
  - `RATE_LIMIT_EXCEEDED`: o usuário pediu de novo em menos de 5 segundos (`429`). Vem com `retry_after`.
  - `SNAPSHOT_RATE_LIMITED`: o recurso recebeu um snapshot há menos de 3 minutos, ou a conta usou a cota das últimas 24 horas (`429`). Vem com `details.scope` (`resource` ou `account`) e `details.retry_after`; com `account`, também `details.resets_at`.
  - `SNAPSHOT_TOO_LARGE`: o conteúdo passa do tamanho que um snapshot deste recurso comporta (`413`). `details.max_bytes` traz o limite.
  - `OPERATION_IN_PROGRESS`: outra operação no mesmo recurso, ou outro snapshot seu, já está em execução (`409`). Nenhum snapshot novo foi feito; a vaga da cota é devolvida.
  - `SNAPSHOT_FAILED`: não foi possível fazer o snapshot. `422` para um banco de dados cujos dados não puderam ser exportados (por exemplo, um banco ainda sem dados): nada foi salvo; adicione dados ou confira o banco e tente de novo. `500` em qualquer outro caso: tente de novo; se continuar, entre em contato com o suporte.
  - `SERVICE_UNAVAILABLE`: o serviço está temporariamente indisponível (`503`). Tente de novo em instantes.
  - `SNAPSHOT_TIMEOUT`: o snapshot demorou demais e foi cancelado (`504`).
  - `INTERNAL_SERVER_ERROR`: o snapshot não pôde ser armazenado, ou ocorreu uma falha inesperada (`500`). Tente de novo mais tarde.
</ResponseField>
