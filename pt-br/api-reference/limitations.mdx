## Limites de recursos por plano

Memória e vCPU vêm do plano; as conexões com o banco de dados são limitadas a 100 por banco em todos os planos. Não há
limite de quantidade de projetos em nenhum plano — o limite real é a RAM do plano: criar uma aplicação ou um banco é
recusado com `MEMORY_LIMIT_EXCEEDED` quando a RAM do plano se esgota.

## Limites de banda

A banda de rede de cada recurso é proporcional à memória alocada a ele.

| RAM | Banda |
|-----|:---------:|
| ≤ 256 MB | 50 Mbit |
| ≤ 512 MB | 100 Mbit |
| ≤ 1.024 MB | 200 Mbit |
| ≤ 2.048 MB | 400 Mbit |
| ≤ 4.096 MB | 800 Mbit |
| ≤ 8.192 MB | 1.600 Mbit |
| ≤ 10.240 MB | 2.000 Mbit |

Recursos com mais de 10 GB de RAM recebem banda escalada em aproximadamente 50 Mbit a cada 256 MB.

contam para elas. A janela por minuto retorna os cabeçalhos `x-ratelimit-limit`, `x-ratelimit-remaining` e
`x-ratelimit-reset`; a janela diária retorna os cabeçalhos `x-quota-limit`, `x-quota-remaining` e `x-quota-reset`. A cota

## Limites de deploy

Criar uma aplicação, enviar um ZIP, fazer deploy a partir do GitHub (manual ou por push), reinstalar dependências e alterar
o build command consomem, todos, um mesmo orçamento horário por conta. Iniciar, parar e um reinício simples não contam;
um reinício com `reinstall_dependencies` ou `force_build` conta. Um push do GitHub além do limite é descartado e
registrado no histórico de atividades. Ao exceder o limite: `429 DEPLOY_RATE_LIMITED`, com `details.limit`,
`details.window_seconds` (3600) e `details.retry_after`.

| Plano | Deploys/hora |
|------|:------------:|
| Starter 1 | 20 |
| Starter 2 | 40 |
| Pro, Business e Enterprise (qualquer tamanho) | 60 |

Rollbacks manuais para uma release anterior têm um orçamento horário separado por conta, com o mesmo teto da tabela
acima. Um rollback não consome vagas de deploy, e um deploy não consome o orçamento de rollback. Ao exceder o limite:
`429 DEPLOY_RATE_LIMITED`, com `details.limit`, `details.window_seconds` e `details.retry_after`. Veja
[Fazer rollback da aplicação para uma release](/pt-br/api-reference/endpoint/apps/releases/rollback).

## Reinício automático

O reinício automático vem ligado por padrão em toda aplicação, em todos os planos, e está sujeito à detecção de loop de
falhas. Se um container falhar **5 vezes em 10 minutos**, o reinício automático é desativado por 24 horas. Há um
**cooldown de 1 hora** entre os reinícios, e o container precisa ficar online por pelo menos **60 segundos** para contar
como estável.

## O que acontece com uma conta sem plano ativo?

Uma conta sem plano ativo não pode criar aplicações ou bancos de dados, nem publicar um site; essas requisições são
recusadas com `PLAN_REQUIRED` (`403`). Projetos que ficarem offline por mais de **30 dias** em uma conta assim são
excluídos automaticamente, com um snapshot feito antes. As notificações são enviadas nos dias 7, 23 e 27.
