Vertra Cloud is a Brazilian application hosting platform (PaaS): deploy from GitHub or a zip file,
isolated containers, managed databases, file storage, snapshots, a CLI, and a VS Code extension.
This page gathers, in one place, every public number of the platform — price, memory, vCPU,
projects, and API limit per plan.

The values below are the same ones used by the platform in production. Prices are in Brazilian
reais. You can buy 1, 3, 6 or 12 months at a time: 3 months get 10% off, 6 months get 15% off and 12 months get
25% off. Pay with PIX or credit card (Visa and Mastercard) on any plan. A plan
paid by card renews automatically on your default card, 3 days before it expires; use **Cancel renewal** in
Billing to stop it. PIX payments never renew by themselves. The prices below are the monthly price.

## How much vCPU does an application actually get?

The vCPU column above is the ceiling per application on the plan, not a total split across the
account's projects. Within that ceiling, a project's vCPU grows with the project's RAM:

- **Growth:** on plans with up to 2 vCPU, +1 vCPU for every 512 MB of RAM; on plans with more than 2 vCPU, +1 vCPU for every 1 GB (1,024 MB).
- **Floor:** a project with 512 MB or more gets at least 2 vCPU; below 512 MB, at least 1 vCPU.
- **Ceiling:** never more than the plan's vCPU. Starter 1 (1 vCPU) gives every project 1 vCPU.

The same rule applies to databases. More RAM never results in less vCPU. A change takes effect the next time the project restarts or is deployed: when your plan changes, the new ceiling reaches each application and database on its next restart or deploy, and nothing restarts by itself.

## What happens to an account without an active plan?

An account without an active plan **can't create applications or databases or publish a site**: those
requests are refused with `PLAN_REQUIRED` (`403`). Subscribe to a plan, starting at Starter 1, to continue.

**Projects that stay offline for more than 30 days on an account without an active plan are automatically
deleted**, with a snapshot taken first and email warnings on days 7, 23, and 27.

## How many custom domains and ports does each plan allow?

Custom domains start at the **Starter 2** plan. The limit is per application and applies to the application owner's
plan. The automatic `www` (or root) companion that comes with a domain **does not count**.

| Plan | Custom domains per application |
|---|---:|
| Starter 1 | 0 |
| Starter 2 | 1 |
| Pro (4, 6 and 8) | 2 |
| Business (12, 16 and 24) | 5 |
| Enterprise (32 to 512) | 20 |

Beyond the plan's domains, every application with domains can serve them on up to **5 different ports besides port
80**; each domain also accepts an optional path prefix and an optional redirect to another domain of the same
application. Reaching the domain limit answers `DOMAIN_LIMIT_REACHED`, and the port limit `DOMAIN_PORT_LIMIT_REACHED`.
A domain that stays `pending`, `moved` or `deleted` for 14 days is removed automatically; after any removal, delete its `CNAME` and `TXT` records at your DNS provider. See
[Connect custom domains](/guides/custom-domain).

[Templates](/templates/overview) follow the same limits: each one needs a minimum plan, calculated from what it creates (applications, databases, Blob, image or web publishing), and image templates use image slots, which start at the Pro plan. The deploy tells you what is missing before it starts.

## Which databases are managed?

There are four managed engines, all with mandatory TLS and certificates (CA, server, and client)
generated automatically by the platform.

| Database | Versions for new databases | User | TLS | Authentication |
|---|---|---|---|---|
| PostgreSQL | **18** (recommended), 17 | `vertracloud` (database `vertracloud`) | Required | Password + client certificate |
| MongoDB | **8.0** (recommended), 9.0 | `vertracloud` (database `vertracloud`, auth database `admin`) | Required | Password + client certificate |
| Redis | **8.2** (recommended), 7.2 | `vertracloud` | Required | User + password + client certificate |
| MySQL | **9.7** (recommended, LTS), 8.4 (LTS) | `vertracloud` (database `vertracloud`) | Required | Password + X509 client certificate |

You choose the version when you create a database (the dashboard selector, or `version` in the API); the recommended
one is the default. Existing databases keep their major version, and security updates (patch releases) are applied
automatically whenever the database is restarted (stop, then start, in the dashboard). If you use `btree_gist` indexes on float columns or `ltree` indexes in PostgreSQL, run `REINDEX` on them after the restart. Existing MySQL 8.0 databases stay
on 8.0, which isn't available for new ones. Existing Redis 7.4 databases stay on 7.4. A database created from a snapshot is born on the snapshot's major version (a MySQL 8.0 snapshot creates a
MySQL 8.4 database, and a Redis 7.4 snapshot a Redis 8.2 one); `version`
can be the same or newer, never older (`SNAPSHOT_VERSION_NEWER`). Restoring a snapshot taken on a newer version into an older database
is refused with the same code and nothing is changed.

`vertracloud` is the user of databases created from v26.4.8 on, and it isn't a superuser. Older databases keep the
engine's user: `postgres` (database `postgres`), `default` on MongoDB (auth database `admin`) and Redis, and `root`
(database `default`) on MySQL. The `username` field of the database in the API tells which one to use.

The port is **unique per database** — not the engine's default — and is shown on the database page. See [how to connect](/databases#how-do-i-connect-to-each-engine).


## What are the limits of the Data tab?

The **Data** tab browses and edits database content through the dashboard or the API, without
exposing the password or the connection string, and requires the **Pro** plan or higher.
Below that plan, the API responds with `PLAN_RESTRICTED_FEATURE` (403).

| Limit | Value |
|---|---|
| Rows, documents, or keys per page | 200 |
| Operation timeout (including SQL console) | 10 s |
| Rows returned by the SQL console | 200 by default, 1,000 max |
| Size of SQL sent to the console | 64 KB |
| Size of the console result | 5 MB serialized |
| Write body (row, document, key value) | 1 MB |
| Items in a Redis collection (list, set, zset, hash, stream) | 1,000 |
| Concurrent console queries per database | 1 |
| Rate limit — SQL console | 30/min per user |
| Rate limit — other data routes | 120/min per user |

Reading applies to any workspace member; **writing and the SQL console are owner or admin only**.
Administrative commands and arbitrary code execution are refused in the Redis and MongoDB console.

| Limit | Value |

| Maximum deploy `.zip` size | 100 MB |

| Maximum build command time (`build_command`) | 10 minutes |
| Storage for an application | 10 GB fixed, regardless of RAM |
| Storage for a database | 6 GB + 1 GB per 512 MB of RAM, rounded to whole GB, or 3× the RAM when larger (from 6 GB of RAM up) |
| Exposed ports per application | Port 80, plus up to 5 more through custom domains |

Network bandwidth is proportional to allocated RAM: 50 Mbit at 100 MB, 100 Mbit at 256 MB, 200
Mbit at 512 MB, 400 Mbit at 1,024 MB, 800 Mbit at 2,048 MB, and 1,600 Mbit at 4,096 MB.

### Deploys-per-hour limit

Counts as a deploy: creating an application, uploading a zip, deploying via GitHub (manual or by
push), reinstalling dependencies, and changing the build command. Restarting and stopping don't
count. A GitHub push that arrives past the limit is ignored and logged in the activity history.

| Plan | Deploys/hour |
|---|---:|
| Starter 1 | 20 |
| Starter 2 | 40 |
| Pro, Business and Enterprise (any size) | 60 |

### Deploy history and rollback limits

Each application keeps the code of its previous versions for a limited time, so you can roll back to
one of them. The version that is running now never expires. A previous version's validity counts from
the moment it stops being the running one.

| Plan | Previous versions kept | Version validity |
|---|---:|---:|
| Starter 1 | 3 | 7 days |
| Starter 2 | 5 | 14 days |
| Pro (4, 6 and 8) | 15 | 30 days |
| Business (12, 16 and 24) | 25 | 30 days |
| Enterprise (32 to 512) | 30 | 30 days |

### Automatic rollback and zero-downtime deploys

**Automatic rollback** (Pro and above): if the new version of an application stops within 60 seconds after a deploy, the platform goes back to the previous version once and notifies you. It is off by default; turn it on in the application's settings.

**Zero-downtime deploys** (Starter 2 and above): the new version starts next to the running one and takes over once healthy. It is off by default (`off`); `auto` applies it to applications that receive web traffic and `on` to every application. See [Update Application Configuration](/api-reference/endpoint/apps/updateconfig) for the setting.
